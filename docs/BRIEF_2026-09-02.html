This did not work the first time, and here is why

If a login looks stuck, this is the fix

Sign in, the page appears, nothing loads, and after a few seconds it returns to the login screen. That is a browser holding a session whose server-side half was destroyed by the bug described in the audit. The tokens are still in the browser and they are no longer valid, so every request fails and the app gives up.

Open the site in a private window, or clear site data for trypcreators.vercel.app, and sign in again. One or the other clears it in seconds. It cannot happen again, because the bug that poisoned the session is fixed, but a browser that was poisoned before the fix stays poisoned until its storage is cleared.

Security audit

A hands-on audit of the live platform, run today against production. Five real vulnerabilities, all fixed and verified. Everything below was proven by making the request, not by reading the code.

How it was tested

Three attacker positions, in order of how likely they are:

  • A stranger with nothing. The publishable API key ships inside the JavaScript bundle, so anybody who has opened the site once has it. Every table and every database function called directly, without signing in.
  • A signed-in creator. A real session token, used against the API directly rather than through the app, trying to read other people's messages, private details and money, and to promote itself to admin.
  • Every server function. All fourteen edge functions called anonymously and as a creator, checking each one's own authentication rather than trusting its configuration.

What was found

Critical Fixed

A stranger could award the prize money

public.award_challenge_prizes_internal(uuid, boolean)

The admin-facing function that awards challenge prizes correctly checks that you are on the team. The internal function it calls, which does the actual work, writes the reward rows, and triggers a draft invoice with the winner's bank details snapshotted into it, and it had no check at all and was callable by anyone. The challenge ID it needs is handed out to anonymous visitors by design, for the landing page.

$ curl -H "apikey: <the key from the JS bundle>" \
  .../rpc/award_challenge_prizes_internal -d '{"p_challenge_id":"f8c2…","p_dry_run":true}'
HTTP 200 · accepted, unauthenticated

Fixed and verified. Now HTTP 401 permission denied. It also carries a second, independent lock inside the function itself, because this is the one that moves money.

High Fixed

A stranger could write to any creator's record

public.milestone_progress(uuid)

This function takes any creator's ID and writes their milestone progress as a side effect of reading it. Unauthenticated, against any account on the platform. It also read back their progress, which is private to them and the team.

Fixed and verified. Now HTTP 401 anonymously, and unchanged for a signed-in creator.

Medium Fixed

The community's data was readable by anyone

best_streak_leaderboard · views_leaderboard · creator_metrics · milestone_state · milestone_overview · route_creators · community_aircraft_gap · can_edit_locale

Eight functions returning creator names, photographs, view counts, wins, per-creator performance metrics and milestone progress, all of it to an unauthenticated caller. Not catastrophic, and not something you would want to explain to a creator who assumed the platform was private.

Fixed and verified. All eight now refuse anonymous callers and work normally when signed in.

High Fixed

An open URL-fetcher, and a lie in the comments

edge function: link-preview · geocode

Both functions were marked as requiring a signed-in user, and both had a comment in the source saying exactly that. It was not true. The gateway setting they relied on accepts the publishable key as a valid credential. It has to, because that is how the browser reaches the database before anybody has logged in. So link-preview was a free URL-fetcher for the entire internet, running on Tryp.com's servers.

$ curl -H "apikey: <the key from the JS bundle>" .../link-preview -d '{"url":"https://example.com"}'
HTTP 200 {"title":"Example Domain","siteName":"example.com"}

Fixed and verified. Both now verify the caller's token cryptographically against the project's public keys, the way the upload and view-sync functions already did, and both carry a per-creator hourly limit. Anonymous callers get 401 sign in first; signed-in creators are unaffected.

High Fixed

The push-notification sender failed open

edge function: notify-dispatch

It checked a shared secret with if (SECRET && header !== SECRET), so so if the secret were ever unset, the check was skipped entirely and anyone could push a notification, with a title, a body and a link of their choosing, to any creator's phone. That is a phishing primitive, not a nuisance. The secret is set in production today, which is the only reason this was latent rather than live; a rotation that briefly cleared it would have opened it.

Fixed and verified. It now refuses to run when the secret is missing.

High Fixed

One bad read signed you out of every device

src/context/AuthContext.jsx

Found because it broke the demo account within an hour of me handing it over. If the app's profile lookup came back with no row, it called supabase.auth.signOut(). That function defaults to global scope: it does not sign this browser out, it revokes every session on the account, on every device.

Two things made that bad. It fired on the first failed read, when a no-rows result is also what a momentary blip looks like. And on a shared account, one person's blip signs all three of you out. When I went looking, the sessions table for the team account was empty, including sessions created forty minutes before the login that triggered it.

Fixed and verified. It retries first, and when it does give up it signs out locally. A genuinely broken login still goes to the login screen; it no longer takes your other devices with it. This affected every creator, not just the demo account.

The cause, and why it will not come back

All ten of the exposed database functions had the same root cause, and it is a Supabase default: every newly created function is granted execute permission to the anonymous role by name and to the public role it inherits from. So a function is born reachable by anybody holding a key that ships in the browser.

This has now bitten this project four separate times. Each previous fix was a hand-written revoke in the migration that created the function, and each was undone by the next migration that touched it. One function was revoked correctly in March and re-exposed three migrations later when it was dropped and recreated.

A rule that has to be remembered by the author of every future change is not a control. So the fix is structural: there is now an explicit allowlist of the five functions the public landing page needs, and a database event trigger that re-applies the correct permissions automatically after any function is created or altered.

$ create a brand new SECURITY DEFINER function, then ask who can call it
  anonymous:   false  ← automatically revoked, nobody wrote a line to do it
  signed-in:   true

What to ask him to look at

Be specific, or you get a generic report. The areas where I would most want a second pair of eyes:

  • Row-level security policies. This is where the platform's entire privacy model lives. Around forty tables, each with its own rules about who can read and write what. I tested the ones that matter most; he should test the ones I did not think of.
  • The permissions on database functions, given that the same mistake has now happened four times. The automatic guard I added today is new and unproven over time, so it is worth him trying to defeat it.
  • The file upload path. It runs with elevated privileges and decides for itself which folder a creator may write into.
  • The admin impersonation feature, "view as creator". It mints a real session for another account. It checks that the caller is an admin, but it is the single most dangerous function on the platform if that check can be turned.
  • Anything a creator submits that another creator sees. Display names, bios, captions, chat messages, admin notes. There was a stored cross-site-scripting bug here in August, fixed then, and this class of bug never stays fixed by accident.

The email thing, since you asked

You have not got email working, and here is the honest state of it. The platform currently sends exactly two kinds of mail: password resets, sent by Supabase, and a welcome email per accepted creator, which an admin approves by hand. Everything else, invoices, announcements and challenge reminders, is written and waiting, and cannot go out.

The blocker is that automated mail from a shared mailbox got the platform flagged as a bulk sender and Gmail started dropping it. The fix is a properly authenticated sending domain: a subdomain like mail.tryp.com with SPF, DKIM and DMARC records set correctly. Sebastian owns DNS and email signing, so this is the one concrete thing to ask him for on this call, and it is small.

The ask, in one sentence

"Can you create a sending subdomain for the creator platform, something something like mail.tryp.com, and add the SPF, DKIM and DMARC records for it? I will send you the exact records; it is three DNS entries and then invoices and challenge announcements can send themselves instead of me doing it by hand."
