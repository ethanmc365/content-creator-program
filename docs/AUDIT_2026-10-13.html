Findings

The view scraper in detail

The scraper reads the view count of every challenge entry and VIP video straight off the link the creator submitted. It replaced an admin opening each video and typing the number. It is the edge function view-sync (about 1,700 lines) with a Facebook module of its own.

What it does
Reads views for entries in running challenges and for VIP videos in the current month, writes them to submissions.logged_views / vip_videos.logged_views, keeps every reading in view_snapshots / vip_view_readings, and queues a points recalculation.
Triggers
Cron view-sync hourly at :07 (re-reads anything older than the 6-hour interval); cron vip-sync hourly at :37 (2-hour interval); database trigger read_new_entry the moment an entry is saved; the admin "Sync now" button; the Testing Centre probe (read-only); vip_close_due forces final reads at month end.
Inputs and outputs
In: the entry's URL, cached platform video id, the creator's Instagram handle. Out: view count, exact or rounded, posted date, thumbnail, error code (blocked, no_count_in_page, not_a_video, ...). Run progress in app_settings.view_sync_run, last run in view_sync_last_run.
External services
TikTok embed pages; YouTube Data API v3 (official, keyed); Instagram public reels tab and GraphQL (signed out); Facebook watch/reel pages. No platform account or cookie is used.
Rate and load
About 810 live entries, each re-read every 6 hours: roughly 135 reads an hour. Concurrency is capped per platform: 8 public reads at once, Instagram 3 with a 120 ms gap, Facebook 2 with a 600 ms gap. One run reads at most 120 entries per chunk and chains up to 40 chunks.
Duplicate-run safety
A run flag (view_sync_running(), 15-minute expiry) turns away a second sweep. The flag is read then written, so an admin press and the cron landing in the same second could still start two runs (finding M1); the effect is entries read twice, not wrong numbers. A forced run never re-reads an entry it already read. A new-entry read now runs quietly beside a sweep instead of being refused.
Overwrite safety
A number typed by an admin (views_source = 'manual') is never overwritten. After a challenge's deadline the sweep stops, so the judged numbers are the deadline numbers.
Failure visibility
Per entry: the error code shows on the results page Sync panel. Instagram: check_instagram_reads raises a system error if every Instagram read in 6 hours failed. New today: ops:views alerts the admin desk and notifies the owner if nothing has been read for 8 hours during a live challenge, or half of the last sweep failed.

Execution flow

  1. pg_cron calls run_view_sync(). It returns early if view sync is disabled, a run is already going, or no challenge is running; otherwise it POSTs to the edge function with the shared webhook secret.
  2. The function authenticates the caller: webhook secret for cron and internal calls, an admin JWT for the button and probes.
  3. It selects up to 120 entries that are due (never read, older than the interval, or never read successfully and last tried over 45 minutes ago), oldest first, and counts the total for the progress bar.
  4. It answers 202 at once and does the work in the background, because pg_net gives up after 5 seconds.
  5. Entries are split into public, Instagram and Facebook lanes and read in parallel within each lane's limit. TikTok, Instagram and Facebook reads that meet a block are retried from other Supabase regions.
  6. Each result is written to the entry and appended to the snapshot table; the points recalculation queue picks up the change within a minute.
  7. If entries are still due, it calls itself with a continuation; otherwise it records the finished run.

Responsible collection

  • YouTube uses the official Data API. TikTok, Instagram and Facebook are read as logged-out web pages, which those platforms' terms of service do not permit for automated collection, and the scraper does not consult robots.txt.
  • Facebook pages are requested with Google's and Bing's crawler user-agents, and blocked reads are retried from other regions. This works, but it presents the reader as a search engine and steps around a block. Tryp should decide whether it is comfortable with that (finding H8).
  • In its favour: it reads only links creators submitted themselves for a paid programme, collects only the public view count, date and thumbnail, uses no account or cookie (the Instagram session was removed after a warning in August), and runs at a polite rate.
  • Safer long-term route: creators connect their own accounts (Instagram Graph API, TikTok Display API, Facebook Graph API), which gives exact counts with the creator's permission and no scraping.
